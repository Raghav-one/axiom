Silicon built for parallel arithmetic

A CPU is a machine for finishing one instruction stream as fast as physics allows. A GPU is a machine for keeping tens of thousands of arithmetic units fed. Everything else — the warp, the memory hierarchy, tensor cores, the entire discipline of kernel optimisation — follows from that single decision about where to spend transistors. This module goes from the transistor tradeoff to multi-GPU collectives, with the mathematics and systems background assumed at zero.

01

Why the GPU exists

The GPU is not a faster CPU. It is the answer to a different question, and the difference is visible in where the transistors go.

Imagine you must deliver ten thousand letters across a city. One strategy is to hire a single courier on a motorcycle that can reach 300 km/h — you optimise the speed of one agent, and you invest heavily in helping that agent make good decisions: which route, which shortcut, what to do when a road closes. The other strategy is to hire five thousand cyclists. No individual cyclist is fast, and you cannot afford to give each one a sophisticated navigation system. But if the letters are independent, the cyclists finish first, by a wide margin.

That is the entire distinction. The motorcycle courier is a CPU core, and it is optimised for latency — the time to finish one task. The cyclists are a GPU, and it is optimised for throughput — the total work completed per unit time. Both are built from the same transistors on the same silicon process. They differ in how those transistors are spent.

Where the transistors go

A modern CPU core devotes the overwhelming majority of its die area to machinery that makes a single instruction stream run fast, none of which performs arithmetic. Branch predictors guess the outcome of an if before it is evaluated. Out-of-order execution engines reorder instructions to work around stalls. Large multi-level caches keep data close. Register renaming, speculative execution, prefetchers — this is control logic, and it is expensive.

A GPU deletes almost all of it. There is no branch predictor worth the name, no out-of-order engine, and a small cache per compute unit. What replaces them is arithmetic units, in enormous quantity, and a scheduler whose only job is to keep them busy.

C

CPU: minimise time-to-answer

Few, very wide cores at high clocks. Deep pipelines, aggressive speculation, large private caches. Excellent on branchy, serial, pointer-chasing code where the next instruction depends on the last.

Wins at: operating systems, databases, compilers, game logic, anything irregular.

G

GPU: maximise work-per-second

Thousands of narrow lanes at modest clocks. Shallow pipelines, no speculation, tiny per-thread cache — but colossal register files and bandwidth. Needs work that is regular and independent.

Wins at: matrix multiply, convolution, rendering, simulation, anything with a wide inner loop.

The central tradeoff The GPU is slower per thread and vastly faster in aggregate. A single GPU thread runs roughly 20–50× slower than a CPU thread on the same serial work. You win only by having enough independent work to fill the machine. This is why "port it to GPU" fails on irregular code and succeeds spectacularly on dense linear algebra.

Why deep learning landed on the GPU

Training a neural network is, computationally, a long sequence of large matrix multiplications. A matrix multiply of two n×n matrices performs about 2n³ arithmetic operations while touching only about 3n² numbers. As n grows, the arithmetic grows faster than the data movement — which is precisely the shape of problem a throughput machine is built for. Deep learning did not choose the GPU because it was convenient; it scaled because the GPU's cost curve happened to match the workload's arithmetic profile.

Common mistake Assuming GPU speedup comes from the clock. It does not — GPUs clock lower than CPUs. All the gain is parallelism and bandwidth. If your problem has a serial dependency chain, or fewer than a few thousand independent work items, the GPU will be slower than a CPU, and no amount of kernel tuning will fix it.
02

Mathematical prerequisites

Four ideas carry almost all of GPU computing: the dot product, the matrix product, operation counting, and the notion of intensity. Assumed knowledge here is arithmetic only.

The dot product — the atom of everything

Take two lists of numbers of equal length. Multiply them position by position, then add up all the products. That single number is the dot product. If one list is [2, 3, 4] and the other is [10, 20, 30], you compute 2×10 + 3×20 + 4×30 = 20 + 60 + 120 = 200.

This pattern — multiply pairs, accumulate the sum — is so central that GPUs implement it as a single hardware instruction called fused multiply-add (FMA): it computes a×b + c in one step, with one rounding instead of two. Every FMA counts as two floating-point operations. When a vendor quotes "67 TFLOPS", they are counting FMAs as two.

The matrix product

A matrix is a rectangular grid of numbers. Multiplying matrix A (size M×K) by matrix B (size K×N) produces C (size M×N), where every entry of C is one dot product: row i of A against column j of B.

The critical observation for hardware: every one of the M×N entries is independent. Nothing about computing C₁₁ depends on C₁₂. You could compute all of them simultaneously, given enough arithmetic units — which is exactly what a GPU provides. This independence is why matrix multiply is the canonical GPU workload, and why the entire deep learning field runs on hardware designed for graphics.

Operation count A matrix multiply of M×K by K×N performs 2·M·N·K floating-point operations — one multiply and one add per term, K terms per output, M·N outputs. For square n×n matrices this is 2n³. Doubling the dimension multiplies the work by eight.

Arithmetic intensity — the number that predicts performance

Here is the idea that governs nearly every optimisation decision in this document. For any computation, ask: how much arithmetic do I perform per byte of data I move? That ratio is arithmetic intensity.

Consider adding two vectors of length n. You read 2n numbers, write n numbers, and perform n additions. In FP32 (4 bytes each) the intensity is n / (12n) = 0.083 FLOP/byte — dreadful. Now consider the square matrix multiply: 2n³ operations against roughly 12n² bytes, giving intensity n/6. At n = 4096 that is about 680 FLOP/byte — four orders of magnitude better.

03

Systems prerequisites

Three laws bound every parallel machine: memory is far away, parallelism has diminishing returns, and concurrency is the product of latency and rate.

The memory wall

Processor arithmetic has improved far faster than memory access time for four decades. The consequence is that a modern chip can perform hundreds of operations in the time it takes to fetch one number from DRAM. Memory is not merely slower — it is slower by a margin that keeps widening.

Concretely: reading a value from a register takes about one clock cycle. Reading the same value from HBM takes roughly 500–600 cycles. If a compute unit sat idle waiting for each fetch, it would be busy less than one percent of the time. Every architectural feature in the rest of this document is, directly or indirectly, a response to this fact.

Little's Law — how much work must be in flight

A result from queueing theory sets the concurrency a throughput machine requires. If you want to sustain a rate of R operations per second, and each operation takes L seconds to complete, then the number of operations that must be simultaneously in progress is their product.

Apply it to an H100: to sustain 3,350 GB/s at roughly 500 ns of memory latency, about 1.6 megabytes of reads must be outstanding at every instant. A single thread issuing one load cannot do this. Thousands of concurrent threads can — and that is the quantitative justification for the GPU's enormous thread count. The thread count is not arbitrary; it is Little's Law solved for the hardware's latency and bandwidth.

This is why GPU work concentrates on kernels that are essentially entirely parallel, and why moving a mostly-serial application to a GPU disappoints.

04

Anatomy of the die

A GPU is a strict hierarchy of replicated units. Understanding the nesting — chip, GPC, TPC, SM, core — makes every performance rule that follows predictable rather than arbitrary.

Zoom in on the die render at the top of this page and the structure is visible: the same block, repeated. That repetition is deliberate. Designing one good compute unit and stamping it out 132 times is far cheaper than designing 132 different units, and it means a defective unit can simply be disabled — which is how a single physical die becomes several product tiers.

HIERARCHY · CHIP → GPC → SM → CORE
Four levels of replication The full chip divides into Graphics Processing Clusters; each GPC holds Texture Processing Clusters; each TPC holds two Streaming Multiprocessors; each SM holds four partitions of CUDA cores, tensor cores, and a register file.

The Streaming Multiprocessor

The SM is the unit that matters. It is the smallest block that independently schedules and executes work, and it is where every resource limit you will ever tune against lives. An H100 has 132 of them; a B200 has 144 across two dies.

Each SM is internally divided into four processing partitions. Each partition has its own warp scheduler, its own dispatch unit, its own slice of the register file, and its own arithmetic units. The four partitions share the SM's L1 cache and shared memory block. This subdivision is why a thread block's resources are allocated in quarters, and why occupancy calculations often produce numbers divisible by four.

Common mistake Believing more SMs automatically means proportionally more performance. A thread block is pinned to a single SM for its lifetime — if your grid launches only 40 blocks on a 132-SM device, 70% of the chip is idle regardless of how well the kernel is written. Grid sizing is a first-order concern, not a detail.
05

SIMT and the warp

Thirty-two threads move as one. This is the single most consequential design decision in GPU programming, and the source of its most expensive performance bug.

A control unit — the logic that fetches an instruction, decodes it, and tells the arithmetic units what to do — is expensive in transistors. Giving every one of 16,896 arithmetic lanes its own control unit would consume most of the die on overhead. The GPU's answer: share one control unit across 32 lanes. One instruction is fetched and decoded once, then broadcast to all 32 lanes, which execute it simultaneously on 32 different data elements.

That group of 32 is a warp, and the execution model is called SIMT — Single Instruction, Multiple Thread. The warp size has been 32 on every NVIDIA GPU since 2006. AMD calls its equivalent a wavefront, historically 64 wide, now 32 on RDNA.

What happens at a branch

All 32 lanes share one program counter, so they must execute the same instruction. What happens when a conditional sends some threads down one path and the rest down another? The hardware cannot execute two instructions at once. Instead it executes both paths sequentially, masking off the lanes that should not participate in each.

divergent.cu — both branches cost full time
__global__ void divergent(float* data) {
    int tid = threadIdx.x;

    // Threads 0-15 take one path, 16-31 the other.
    // The warp executes BOTH bodies, one after the other.
    if (tid < 16) {
        data[tid] = expensive_a(data[tid]);   // lanes 16-31 masked off, idle
    } else {
        data[tid] = expensive_b(data[tid]);   // lanes 0-15 masked off, idle
    }
    // Cost = time(a) + time(b), not max(a, b).
}

// FIX: align the branch to warp boundaries so whole warps
// take the same path — then there is no divergence at all.
if ((tid / 32) % 2 == 0) { ... } else { ... }
The worst case A switch with 32 arms, where every lane takes a different arm, serialises into 32 passes at 1/32 utilisation — a 32× slowdown on that region. Divergence between different warps is completely free; only divergence within a warp costs anything. Restructure data so that threads in the same warp follow the same control path.

Independent thread scheduling

Since Volta (2017), each thread maintains its own program counter, and the hardware may interleave divergent paths rather than strictly serialising them. This enables correct fine-grained synchronisation inside a warp, but it also broke a great deal of older code that implicitly assumed lockstep execution. The modern rule is explicit: use __syncwarp() where you need warp-level agreement, and always use the _sync variants of shuffle and vote intrinsics.

06

Latency hiding

The GPU never makes a memory access fast. It makes the wait invisible by always having another warp ready to run.

A CPU faced with a cache miss stalls, and spends its transistors on speculation and prefetching to avoid stalling. A GPU takes the opposite approach: when a warp issues a memory request and cannot proceed, the scheduler simply switches to a different warp in the same clock cycle, with zero switching cost.

The zero cost is the essential trick. On a CPU, a context switch means saving registers to memory and restoring others — hundreds of cycles. On a GPU, every resident warp's registers stay permanently in the register file. Nothing is saved or restored; the scheduler just selects a different set of registers to read. This is why the register file is enormous (64 KB per partition, 16 MB across an H100 — larger than its L2 cache).

07

The memory hierarchy

Five tiers, spanning three orders of magnitude in latency and four in capacity. Nearly all GPU optimisation is the art of moving data upward and keeping it there.

Fast memory is small and expensive; large memory is slow and cheap. No technology escapes this, so every processor builds a pyramid: a little very fast storage near the arithmetic units, backed by progressively larger and slower tiers. What distinguishes the GPU is that one of its tiers — shared memory — is not a cache at all, but a scratchpad the programmer controls explicitly.

Shared memory — the programmable tier

Shared memory is a block of SRAM inside each SM, addressable directly by the programmer. It is roughly 20× faster than global memory and visible to every thread in a block. The canonical usage pattern is load once, reuse many times: cooperatively stage a tile of data from HBM into shared memory, synchronise, then have every thread in the block read that tile repeatedly at SRAM speed.

tiled_matmul.cu — the fundamental GPU idiom
#define TILE 32

__global__ void matmul_tiled(const float* A, const float* B,
                             float* C, int N) {
    // Scratchpad in SM-local SRAM — explicitly managed.
    __shared__ float As[TILE][TILE];
    __shared__ float Bs[TILE][TILE];

    int row = blockIdx.y * TILE + threadIdx.y;
    int col = blockIdx.x * TILE + threadIdx.x;
    float acc = 0.0f;

    for (int t = 0; t < N / TILE; ++t) {
        // 1. Cooperative load: HBM -> shared. One trip.
        As[threadIdx.y][threadIdx.x] = A[row * N + t * TILE + threadIdx.x];
        Bs[threadIdx.y][threadIdx.x] = B[(t * TILE + threadIdx.y) * N + col];
        __syncthreads();          // tile is now complete

        // 2. Reuse: each loaded value is read TILE times from SRAM.
        #pragma unroll
        for (int k = 0; k < TILE; ++k)
            acc = fmaf(As[threadIdx.y][k], Bs[k][threadIdx.x], acc);

        __syncthreads();          // before overwriting the tile
    }
    C[row * N + col] = acc;
}
// Arithmetic intensity improves by a factor of TILE (32x here),
// which is what moves this kernel across the roofline ridge.
Why tiling is the whole game The naive matmul reads 2N values from HBM per output element. The tiled version reads 2N/TILE. With TILE = 32 that is 32× less memory traffic for identical arithmetic — arithmetic intensity multiplied by 32. Section 11 shows precisely why that moves the kernel from bandwidth-limited to compute-limited.
Both barriers are required Omitting the second __syncthreads() is a classic race: fast threads begin overwriting the tile for iteration t+1 while slower threads are still reading it for iteration t. The kernel produces almost correct results, non-deterministically — the hardest class of bug to find.
08

Coalescing and bank conflicts

Two access-pattern rules, one for global memory and one for shared memory. Violating either silently costs an order of magnitude.

Global memory: coalescing

The memory system does not transfer individual values. It moves fixed-size transactions of 32 bytes, and a request for a single 4-byte float causes the full 32-byte sector to be fetched regardless. When the 32 threads of a warp issue loads simultaneously, the hardware attempts to merge them into as few transactions as possible.

If the warp reads 32 consecutive floats — 128 contiguous bytes — the hardware satisfies it with four 32-byte transactions and every byte fetched is used. This is coalesced access. If those same 32 threads read floats scattered across memory, each may land in a separate sector: 32 transactions, 1,024 bytes moved to deliver 128 useful bytes. Same instruction, same thread count, 8× the traffic.

Shared memory: bank conflicts

Shared memory is physically divided into 32 banks, each 4 bytes wide, interleaved so that consecutive 4-byte words land in consecutive banks. All 32 banks can be accessed in the same cycle — provided the 32 lanes of a warp touch 32 different banks. When two lanes address different addresses in the same bank, the accesses serialise.

The classic trigger is a shared array of width 32 accessed by column: tile[threadIdx.x][k] makes every lane hit bank k — a 32-way conflict and a 32× slowdown on that access. The standard fix is one line: pad the row width by one element.

padding.cu — a single element that removes a 32× penalty
// BAD: column access hits one bank 32 ways.
__shared__ float tile[32][32];
float v = tile[threadIdx.x][k];     // stride 32 words -> same bank

// GOOD: pad the row to 33. Now element [i][k] sits in
// bank (33*i + k) % 32 = (i + k) % 32 — all 32 lanes differ.
__shared__ float tile[32][33];
float v = tile[threadIdx.x][k];     // conflict-free

// Costs 128 extra bytes of shared memory per tile.
// Recovers up to 32x on the access. Always worth it.
The exception A broadcast is free. If all 32 lanes read the same address, the hardware serves them from one bank in a single cycle. Conflicts arise only from different addresses within the same bank — reading identical data costs nothing extra.
09

Tensor cores

A CUDA core multiplies two numbers. A tensor core multiplies two small matrices in a single instruction — and that difference accounts for the last decade of AI compute growth.

By 2017 it was clear that neural networks spend nearly all their time in matrix multiplication, and that general-purpose FP32 lanes were an inefficient way to do it. The response was a dedicated unit that consumes entire matrix tiles as operands. Where a CUDA core executes a×b+c on scalars, a tensor core executes D = A×B + C where each operand is a small matrix — a 4×4×4 tile is 128 FLOPs from one instruction.

The efficiency gain is structural. A scalar FMA must fetch operands, decode, and route results for every single multiply-add. A tensor core amortises all of that overhead across hundreds of arithmetic operations, and hard-wires the internal data movement in silicon rather than paying for it in register reads.

Programming them

Tensor cores operate at warp scope: all 32 threads cooperate to supply one MMA operation, with each thread holding a fragment of the operand tiles in its registers. You rarely write this directly — cuBLAS, cuDNN and CUTLASS emit it — but the API makes the model explicit.

wmma.cu — warp-level matrix multiply–accumulate
#include <mma.h>
using namespace nvcuda::wmma;

__global__ void tc_matmul(const half* A, const half* B, float* C, int N) {
    // Fragments are distributed across all 32 lanes of the warp.
    fragment<matrix_a, 16,16,16, half, row_major> a_frag;
    fragment<matrix_b, 16,16,16, half, col_major> b_frag;
    fragment<accumulator, 16,16,16, float> acc_frag;   // FP32 accumulate

    fill_fragment(acc_frag, 0.0f);

    for (int k = 0; k < N; k += 16) {
        load_matrix_sync(a_frag, A + k, N);
        load_matrix_sync(b_frag, B + k, N);
        // 16x16x16 = 8192 FLOPs issued as ONE warp instruction.
        mma_sync(acc_frag, a_frag, b_frag, acc_frag);
    }
    store_matrix_sync(C, acc_frag, N, mem_row_major);
}
Mixed precision, stated precisely Inputs are low precision (FP16/BF16/FP8); the accumulator is FP32. This is what makes reduced precision safe: individual products are coarse, but the running sum — where error would otherwise compound across thousands of terms — is kept wide. "Mixed precision" means exactly this split, not uniformly lower precision.
Alignment requirements Tensor cores engage only when tile dimensions are multiples of the native MMA shape (typically 16, or 8 for some formats) and operands meet alignment rules. A GEMM with K = 4095 can silently fall back to CUDA cores and run an order of magnitude slower. Pad dimensions to multiples of 16 — for FP8 on Hopper, prefer multiples of 32.

Numeric formats

Every bit removed from a number doubles potential throughput and halves memory traffic. The entire discipline is deciding which bits are safe to remove.

Recall the three-part structure from section 2: sign, exponent, mantissa. The exponent buys dynamic range — the span between the largest and smallest representable magnitude. The mantissa buys precision — how finely adjacent values are separated. Formats differ almost entirely in how they split a fixed bit budget between the two.

Why BF16 displaced FP16 for training

FP16 has only five exponent bits, capping its maximum at 65,504 and — more dangerously — underflowing to zero below about 6e-5. Gradients in deep networks routinely fall below that threshold, vanishing silently and stalling training. The historical workaround, loss scaling, multiplies the loss by a large constant to lift gradients into representable range, then divides it out before the optimiser step.

BF16 solves this by construction. It keeps FP32's full eight-bit exponent, so it has identical dynamic range and cannot underflow where FP32 would not. It pays with mantissa bits — roughly two decimal digits of precision — which turns out to matter far less for gradient descent than range does. Conversion to and from FP32 is also trivial: truncate or zero-pad the low 16 bits.

The governing rule Range matters more than precision in training; precision matters more in inference. Training accumulates many small updates and must not lose them to underflow. Inference performs a fixed forward pass over a known activation distribution, where values can be calibrated into a narrow range and represented coarsely.
Two FP8 formats, deliberately E4M3 (more mantissa) suits forward activations and weights, whose values cluster in a known range. E5M2 (more exponent) suits gradients, which span many orders of magnitude. Hopper's Transformer Engine tracks per-tensor statistics at runtime and selects the format and scaling factor automatically — the format choice is a property of the tensor, not the layer.
Quantisation is not free Reduced precision multiplies theoretical FLOPS but does nothing for a memory-bound kernel except halve its bytes — and if you must convert formats on the fly, the conversion itself costs bandwidth. Confirm a kernel is compute-bound (section 11) before assuming lower precision will speed it up.

The roofline model

One chart that tells you the maximum performance any kernel can achieve on any machine, and — more usefully — which of the two resources is stopping you.

Williams, Waterman and Patterson formalised this in 2009, and it remains the most useful single diagram in performance engineering. The reasoning is simple. A kernel with arithmetic intensity I running on hardware with peak bandwidth B can, at best, supply data fast enough to sustain I × B FLOP/s. It also cannot exceed the machine's peak arithmetic rate P. Actual attainable performance is therefore the smaller of the two:

Plotted on logarithmic axes this produces a slanted line that rises with intensity, then flattens into a horizontal ceiling. The corner where they meet is the ridge point, and it is a property of the hardware alone:

Reading the diagnosis

The model turns a vague question ("why is my kernel slow?") into a decision with two branches. Locate your kernel's intensity on the horizontal axis; compare it to the ridge point.

←

Left of the ridge: memory-bound

You are limited by bandwidth. Extra FLOPS are worthless. Fix by raising intensity: fuse adjacent kernels to avoid round trips, tile into shared memory for reuse, use smaller data types to move fewer bytes, and improve coalescing so no fetched byte is wasted.

→

Right of the ridge: compute-bound

You are limited by arithmetic. Moving data faster changes nothing. Fix by raising throughput: engage tensor cores, drop to a lower-precision format, exploit structured sparsity, and remove instruction-level inefficiency such as divergence or register spills.

The ridge keeps moving right Compute has grown far faster than bandwidth for two decades. The V100's BF16-equivalent ridge sat near 139 FLOP/byte; the H100's is about 295; in FP8 terms it passes 590. Kernels that were comfortably compute-bound on older hardware become memory-bound on newer hardware without a line changing. This single trend explains why kernel fusion, FlashAttention, and KV-cache compression became urgent — the hardware moved beneath the software.
Where the simple model misleads The basic roofline assumes perfect caching and infinite parallelism. A kernel far below the roof is often limited by something the chart does not show: insufficient occupancy to hide latency, warp divergence, atomic contention, or L2 thrash. Treat the roofline as an upper bound and a first diagnosis, then confirm with a profiler such as Nsight Compute.

GEMM — the ideal workload

General matrix multiply is the operation GPUs are effectively designed around. Following how a fast GEMM is built explains most of what a fast kernel does in general.

GEMM computes C ← αAB + βC. It is the computational core of dense layers, attention projections, convolutions after transformation, and most classical linear algebra. On a well-tuned implementation it reaches 80–95% of a GPU's theoretical peak — a level almost no other operation approaches.

The hierarchy of tiling

A production GEMM tiles the problem at every level of the memory hierarchy simultaneously, with each level's tile sized to that level's capacity. The pattern mirrors the hardware hierarchy from section 4 exactly.

Software pipelining

Tiling alone leaves the arithmetic units idle during each tile load. The remedy is double buffering: while the tensor cores compute on tile k, the memory system asynchronously fetches tile k+1 into a second shared-memory buffer. Compute and data movement overlap, and the load latency disappears behind useful work.

Hopper made this a first-class hardware feature. The Tensor Memory Accelerator (TMA) performs asynchronous multidimensional copies from global to shared memory without consuming registers or occupying threads in an address-generation loop — a single thread issues the descriptor and the copy engine handles the rest.

pipelined.cu — overlap the fetch with the math
__shared__ float buf[2][TILE][TILE];   // two stages

load_tile(buf[0], 0);                     // prologue: prime the pipe
__syncthreads();

for (int k = 0; k < nTiles; ++k) {
    int cur = k & 1, nxt = cur ^ 1;

    // Issue the NEXT load asynchronously — does not block.
    if (k + 1 < nTiles)
        cp_async(buf[nxt], tilePtr(k + 1));

    // Compute on the CURRENT tile while that load is in flight.
    mma_accumulate(acc, buf[cur]);

    cp_async_wait();               // now the next tile has landed
    __syncthreads();
}
// Memory latency is hidden behind arithmetic, not added to it.
Why GEMM hits peak and your kernel does not GEMM has O(n³) arithmetic over O(n²) data — intensity that grows without bound as the problem grows. Almost nothing else does. Element-wise operations are stuck at O(n) over O(n), permanently memory-bound no matter how they are written. The shape of the algorithm, not the quality of the code, sets the ceiling.
Wave quantisation A GEMM is decomposed into thread blocks distributed across SMs. If it produces 140 blocks on a 132-SM device, the machine runs one full wave then a second wave of 8 blocks — the second wave costs as much wall-clock time as the first while using 6% of the chip. Efficiency drops to about 53%. Batch sizes and tile shapes should be chosen so block counts land near a multiple of the SM count.

FlashAttention — a case study

Everything so far, applied to one operation. FlashAttention changes no mathematics and computes an exact result; it simply refuses to write the intermediate to memory.

Attention, the core operation of the transformer, is defined as:

Implemented literally, this materialises the matrix S = QKᵀ, which has shape N×N for sequence length N. At N = 8192 in BF16 that single intermediate occupies 128 MB per attention head — written to HBM, read back for the softmax, written again, and read once more for the multiplication by V.

The arithmetic is O(N²d); the memory traffic is O(N²). Intensity is roughly d — about 64 or 128 — which sits far to the left of the H100's ridge point of 295. Standard attention is decisively memory-bound, and the GPU spends most of its time moving a matrix it does not need to keep.

STANDARD vs. TILED · HBM TRAFFIC
The intermediate that never exists Top: the full N×N score matrix round-trips to HBM three times. Bottom: FlashAttention streams tiles through SRAM, computing softmax incrementally and writing only the final output.

The insight: never materialise S

The obstacle is the softmax, which appears to require a full row before it can normalise — every element of the row must be seen to compute the denominator. The resolution is the online softmax: maintain a running maximum and a running sum, and rescale accumulated results whenever a new tile reveals a larger maximum.

The correction factor e^(m_old − m_new) retroactively fixes every previously accumulated value when the maximum shifts. The result is numerically identical to standard softmax — this is exact attention, not an approximation.

flash_attention.py — the tiled loop, in outline
# Q, K, V: [N, d].  Tiles sized to fit SRAM (~228 KB per SM).
O = zeros(N, d); l = zeros(N); m = full(N, -inf)

for j in range(0, N, B_c):              # outer: blocks of K, V
    K_j = K[j:j+B_c]; V_j = V[j:j+B_c]   # HBM -> SRAM, once

    for i in range(0, N, B_r):          # inner: blocks of Q
        Q_i = Q[i:i+B_r]

        S_ij = Q_i @ K_j.T / sqrt(d)     # stays in SRAM — never stored

        m_new = maximum(m[i], S_ij.max(axis=-1))
        P_ij  = exp(S_ij - m_new)
        # Rescale prior accumulation to the new maximum.
        alpha = exp(m[i] - m_new)
        l[i]  = alpha * l[i] + P_ij.sum(axis=-1)
        O[i]  = alpha * O[i] + P_ij @ V_j

        m[i] = m_new

O = O / l[:, None]                       # single normalisation at the end
# HBM traffic: O(N*d) instead of O(N^2). Result: bit-exact.

The transferable lesson FlashAttention performs more arithmetic than the standard implementation — it recomputes parts of the attention matrix in the backward pass rather than storing them — and is substantially faster anyway. On memory-bound problems, trading extra computation for less data movement is almost always the right trade. This is the single most useful heuristic in modern GPU optimisation.

Occupancy and launch configuration

Registers, shared memory, and block size compete for one fixed budget. Tuning them is arithmetic, not guesswork.

Each SM can host at most 64 warps, 2,048 threads, 32 blocks, 64 K registers and 228 KB of shared memory. A kernel's resource demands determine which of these binds first, and that limit sets the achieved occupancy.

Higher occupancy is not the objective Occupancy measures capacity to hide latency, not speed. A kernel holding many values in registers may run at 25% occupancy and outperform a 100%-occupancy version that spills to local memory. Volkov demonstrated in 2010 that low-occupancy kernels with high instruction-level parallelism frequently win. Optimise for time, and treat occupancy as a diagnostic.
Register spilling Exceed the per-thread register budget and the compiler moves variables to "local" memory — which is physically global memory, hundreds of cycles away, despite the name. A kernel that spills can lose an order of magnitude. Compile with -Xptxas -v to see register counts and spill stores per kernel; treat any spill in a hot loop as a defect.

Block size 128–256

Divisible by 32, large enough to amortise launch and barrier cost, small enough to divide the SM evenly. Start at 256 and measure.

2

Grid ≥ 4× SM count

Gives the scheduler enough blocks to balance load and absorb wave quantisation. Below one block per SM the chip is idle by construction.

3

Cap registers deliberately

__launch_bounds__ tells the compiler your target occupancy so it budgets registers accordingly instead of optimising one warp in isolation.

Multi-GPU scale-out

Frontier models exceed any single device's memory by orders of magnitude. Splitting them across hundreds of GPUs turns the interconnect into the new bottleneck.

A 405-billion-parameter model in BF16 requires 810 GB for weights alone. Training state — gradients plus Adam's two optimiser moments — typically multiplies that by roughly six, reaching several terabytes before a single activation is stored. No single GPU comes close, so the model must be partitioned, and partitioning means communication.

The four parallelism strategies

Each splits a different axis of the computation, and each stresses a different part of the network. Production runs at scale combine all four, an arrangement usually called 4D parallelism.

D

Data parallel

Every GPU holds a full model replica and processes a different micro-batch. Gradients are averaged with an all-reduce each step.

Communication: 2× parameter bytes per step. Limit: the model must fit on one device.

T

Tensor parallel

Individual weight matrices are split across GPUs; each computes a slice of every layer. Requires an all-reduce within each layer.

Communication: very high, twice per layer. Limit: keep inside one NVLink domain — typically ≤8 GPUs.

P

Pipeline parallel

Layers are assigned to different GPUs in sequence; micro-batches flow through the stages like an assembly line.

Communication: low — activations at stage boundaries only. Limit: pipeline "bubbles" idle stages at the start and end of each batch.

E

Expert parallel (MoE)

Different experts of a mixture-of-experts layer live on different GPUs; tokens are routed to their selected experts and back.

Communication: two all-to-all exchanges per MoE layer. Limit: load imbalance when routing is skewed.

Ring all-reduce The standard gradient-averaging algorithm arranges GPUs in a ring and moves 2(N−1)/N times the data per GPU — asymptotically independent of GPU count. This bandwidth-optimality is why data-parallel training scales to thousands of devices instead of collapsing under a central-server bottleneck.
Where scaling actually dies Tensor parallelism across a slow link is the classic failure. Inside an NVLink domain it is nearly free; spanning nodes over InfiniBand, the per-layer all-reduce becomes 30× more expensive and can consume more time than the arithmetic it enables. Map the parallelism strategy onto the physical topology — tensor within a node, pipeline and data across nodes.

The divergence that shapes everything Between V100 and B200, tensor throughput at comparable precision rose about 36× (125 TF FP16 → 4.5 PF BF16) while memory bandwidth rose only 8.9×. Compute is outpacing bandwidth by roughly 4× — and comparing V100 FP16 against B200 FP4, the widest honest framing, the gap reaches 144×. This is why the ridge point keeps sliding right, why more kernels become memory-bound each generation, and why techniques that trade arithmetic for data movement — fusion, recomputation, FlashAttention, quantised KV caches — keep getting more valuable rather than less.
Reading vendor numbers honestly Headline FLOPS figures often assume structured sparsity (a 2× multiplier requiring a 2:4 zero pattern most models do not have) and the narrowest supported format. A B200's "20 PFLOPS" is FP4 with sparsity; dense BF16 is 4.5 PF — a 4.4× difference. Always check the format, the sparsity assumption, and whether the number is per-GPU or per-package.
